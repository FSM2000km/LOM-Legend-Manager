# 活俠伝 伝説管理ツール 作業プロトコル

## 目的

活俠伝の伝説エクスポートファイルを、出力時刻だけのファイル名から、ED名・結縁相手・タグで管理できる状態にする。

実装は次の2系統に分ける。

- BepInEx監視MOD: ゲーム内IDの取得、伝説ファイルの検出、リネーム、JSONイベント出力を行う。
- Pythonデスクトップビューワ: JSON受信、ファイル走査、SQLite更新、一覧、検索、本文閲覧、タグ編集、手動補正を行う。

SQLiteへ書き込むプロセスはPythonビューワだけとし、MODとDB接続を共有しない。

ローカルHTTPサーバーや外部Webデプロイは初期実装の対象外とする。

### 初期実装の範囲

- 初期実装は、ゲーム標準の伝説エクスポートで生成されるED記録だけを対象とする。
- 死亡画面にはゲーム標準の伝説エクスポート処理がないため、死亡記録の独自エクスポートは初期実装へ含めない。
- 生死簿タイトルの抽出データは将来拡張用としてプリセットに残すが、初期実装では分類、リネーム、タグ付け、検索対象にしない。
- 死亡記録への対応は、ED管理MVPの完成後に独立した拡張フェーズとして検討する。

## 基本原則

- 日本語表記は日本語化MOD JP v2.4の翻訳テーブルに準拠する。
- 実行時に日本語化MODのZIPや別MODの用語集へ依存しない。
- 開発時に抽出したプリセットJSONを伝説管理側に同梱する。
- 伝説本文に実際に出た出来事は通常タグとして扱う。
- 未観測ルートや未発生条件を示唆する推測タグはデフォルトでは表示しない。
- ユーザーが手動修正したメタデータは自動解析で上書きしない。
- 同一本文の重複ファイルは削除しない。
- リネーム履歴ファイルは作らない。ただしDBには元ファイル名を保存してよい。

## ファイル名仕様

通常判定できた場合:

```text
{filePrefix}_{ED名}_{結縁相手}_{出力日時}_{hash8}.txt
```

例:

```text
ED48_武林（ぶりん）伝説_小師妹_20260723013650_35c24603.txt
```

判定不能の場合:

```text
ED名不明_結縁相手不明_{出力日時}_{hash8}.txt
```

ファイル名安全化:

- Windows禁止文字 `\ / : * ? " < > |` は全角または安全文字へ置換する。
- 改行、タブ、連続空白は単一空白へ正規化する。
- 末尾のピリオドと空白は削除する。
- ファイル名が長すぎる場合は、ED名側を短縮し、`hash8` は必ず残す。

## 確定タグの本文追記

HTML版UIとPythonデスクトップビューワの両方に、`確定済みのタグを文頭に追記する` ボタンを設ける。

Pythonデスクトップビューワでは、選択中の伝説TXT本体の先頭へ次の管理ブロックを直接書き込む。

```text
【確定済みタグ】
ED48 武林（ぶりん）伝説
小師妹
小師妹生存
大師兄生存
金烏討伐成功
西武林盟成立
眉山決戦
【確定済みタグここまで】

```

追記対象:

- ED名
- 結縁相手または `無結縁`
- 本文で観測済みの生存、加入、留学、移動、出来事タグ
- ユーザーが確定した手動タグ

追記対象外:

- 隠し候補タグ
- `inferred_absence` を根拠とするタグ
- `重複`、`低信頼`、`手動確認`、`短文`、`未分類` などの管理用タグ
- `ED名不明`、`結縁相手不明`

書き込み規則:

- 同名タグは一度だけ書く。
- 順序は、タイトル、結縁相手、生存、加入、留学・移動、観測済みイベント、手動タグの順で固定する。
- 既存の管理ブロックがある場合は追記せず、ブロック全体を現在の確定タグで置換する。
- 管理ブロック以外の本文バイト列は変更しない。
- 元ファイルのUTF-8 BOM有無と改行コードを維持する。
- 同一ディレクトリの一時ファイルへ書いた後、元ファイルと原子的に置換する。
- 書き込み失敗時は元ファイルとDB状態を変更せず、エラーを表示する。
- 確定タグが変更された場合は、UIに `本文タグ要更新` と表示する。

重複判定とファイル名の `hash8` には、管理ブロックを除外した本文のSHA-256を使用する。現在のファイル全体のSHA-256は監査用に別項目へ保存する。

静的HTMLモックでは、対応ブラウザのファイルアクセスAPIを使い、ユーザーが選択して書き込みを許可したTXTへ直接書き込む。未対応ブラウザでは書き込みを行わず、利用できないことを表示する。Pythonデスクトップビューワでは、一覧で選択中のTXTへ直接書き込む。

## タグ仕様

### 通常表示タグ

本文で観測された事実のみ通常タグにする。

例:

- `小師妹生存`
- `大師兄生存`
- `金烏討伐成功`
- `西武林盟成立`
- `崆峒留学`
- `青城留学`
- `錦香宮`
- `無結縁`
- `重複`

### 隠し候補タグ

本文に出ていないが、解析上推測できるものは隠し候補にする。

例:

- `金烏未討伐`
- `大師兄救出失敗`

### タグ属性

各タグには最低限次を持たせる。

```json
{
  "name": "金烏討伐成功",
  "visibility": "public",
  "basis": "observed_in_text",
  "confidence": "high",
  "source": "auto"
}
```

`visibility`:

- `public`: 通常表示
- `hidden_candidate`: 隠し候補

`basis`:

- `observed_in_text`: 本文に実際に出た
- `manual`: ユーザー手動
- `preset`: プリセット由来
- `inferred_absence`: 未観測から推測

`source`:

- `auto`
- `manual`

## SQLite方針

SQLiteを主DBにする。MODのJSONはプロセス間受渡し専用であり、Pythonが取込後に`processed`へ移動する。DBバックアップはSQLite Backup APIで作成する。

### 最低限のテーブル

`legends`は、イベントID、本文ハッシュ、正規化ハッシュ、ファイル全体ハッシュ、元名、現名、絶対パス、出力日時、ED、結縁相手、各情報源、Story key、重複先、メモ、タグ追記日時、欠落状態を保持する。

`legend_text`は管理ブロックを除いた本文を保持し、一覧検索に使用する。

`tags`はカタログID、表示名、カテゴリ、既定表示、順序、ネタバレ候補状態を保持する。

`legend_tags`は伝説とタグの対応、情報源、信頼度、確定状態を保持する。

`tag_suppressions`はユーザーが外した自動タグを保持し、再走査で勝手に復活させない。

`audit_log`は手動タグ、確定情報などの操作内容を保持する。ファイルリネーム履歴は作らない。

`schema_meta`と`PRAGMA user_version`はDBスキーマ版とJPプリセット版を保持する。

DBは`journal_mode=DELETE`、`synchronous=FULL`、`foreign_keys=ON`、`busy_timeout=5000`とし、単一Pythonプロセスだけが書き込む。

## エラー処理

ファイル読み込み失敗:

- リトライする。
- 失敗したらDBに登録せず、ログへ残す。

判定不能:

- `ED名不明`
- `結縁相手不明`
- `confidence = low`
- `手動確認` タグを付ける。

リネーム先が既に存在:

- `hash8` が同じなら重複としてDBに登録する。
- ファイル名衝突だけなら末尾に `_2`, `_3` を付ける。

JSONイベント出力失敗:

- MODログへ残す。
- TXTは削除せず、Pythonのファイル走査で最低限の登録を補完できるようにする。

DB書き込み失敗:

- Python側でトランザクションをロールバックする。
- 取込失敗イベントを`failed`へ移動し、例外内容を併記する。

## 受け入れ基準

初期完成:

- 既存18件をリネームせずSQLiteへ取り込める。
- ED名が日本語化MOD準拠で出る。
- 結縁相手不明時の扱いが決まっている。
- 重複を削除せず認識できる。
- 監視MODが新規ファイルを処理できる。
- Pythonビューワで一覧と本文を確認できる。

品質基準:

- 既存ファイルは明示操作なしにリネームも本文更新もされない。
- 文字化けしない。
- 手動修正が自動解析で消えない。
- 他MODのファイルがなくても伝説管理MODは動く。
- 日本語化MODの表記更新に備えてプリセットバージョンを持つ。
- タグを文頭へ追記しても、管理ブロックを除外した本文ハッシュと `hash8` は変化しない。
